# Phase 08 - SmartOmni-side requirements (BLOCKED here)

The simulator side (conversation API, demo chat, events, test controls) is implemented in this repo. The items below belong to the SmartOmni platform repo (reference only for this work) and are NOT implemented or tested. All contract facts are `unverified` in `contracts/manifest.json`.

1. **Sync window**: sync conversations/messages only from the moment the TikTok connection is made (product decision); the simulator deliberately exposes older seeded history (`create_time` in 2026-10-12) so this filter can be tested. Never import pre-connection history.
2. **Dedupe**: unique constraint on (connection, external message id) for polling AND webhooks; a duplicate NEW_MESSAGE (same `tts_notification_id`, produced by the Test Console "Duplicate event") must not create a second message. A lost event (Test Console "Lose event") must be recovered by polling `GET /customer_service/202309/conversations/{id}/messages` with a per-conversation watermark (`index`/`create_time`).
3. **Identity**: keep `user_id` (order-queryable) and `im_user_id` (IM only) separate. Link a conversation to an order/customer only when `user_id` matches a verified order buyer. The seeded unlinked conversation (`tt-unknown-*`) must stay unlinked and never be attached to an order.
4. **Inbox API**: list/read/reply for authorized staff with tenant + connection scoping; audit sender, time and outcome of each reply. Reply through the same adapter as production (`POST /customer_service/202309/conversations/{id}/messages`, TEXT, `content` = `{"content":"..."}` serialized string, max 2000 chars). Send Message 202606 is NOT available in the simulator (no schema snapshot).
5. **Indeterminate send**: a timeout, or a dropped response (Test Console "Drop send response": the message IS stored and its event emitted), means the outcome is UNKNOWN. Do not retry blindly (the API has no idempotency key, a retry creates a duplicate); reconcile by polling before resending, and show "unknown" in the UI.
6. **can_send_message=false** must disable the reply box and be surfaced instead of attempting a send.
7. **AI gateway**: the Java AI gateway should classify normal vs complaint only (no drafting or sending). The Python classifier lives outside both repos: any integration test in this area must use a clearly labelled TEST DOUBLE and the report must say real-AI testing is BLOCKED. The simulator's `complaint test label` is seed data for building scenarios, never a classifier result.
8. **Complaint session lock**: after a complaint is detected, later messages skip the classifier and go to Staff until Staff marks it resolved.
9. **Unsupported content**: IMAGE/VIDEO/card types are never created by the simulator; the adapter must show a placeholder (use `unsupported_msg_tips`) and not crash on unknown `type` values (the seed contains a `NOTIFICATION` message with `is_visible=false` that must not be shown to staff).
